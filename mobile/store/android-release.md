# Google Play release build

The `Android Play release bundle` workflow creates a production AAB for `com.indiagully.app`. It is manually started on `main` and does not upload to Google Play or publish a release. The regular `Mobile app builds` workflow continues to provide a development-key-signed APK for review.

## One-time owner setup

1. Confirm the app record and package name in the owner's Play Console. Enable Play App Signing there; Google manages the app-signing key, while the company retains a separate upload key.
2. Reuse the existing approved upload key if one exists. For a first release, the owner or authorized release administrator can create one through Android Studio's **Generate Signed Bundle / APK** flow, or with `keytool -genkeypair`. Use a private key with a long-lived certificate and retain an encrypted backup in the company password manager. Do not put the keystore or passwords in Git, a chat, or build artifacts. No key is generated by this workflow.
3. Create the GitHub environment `android-production` under the repository's **Settings → Environments**. Restrict deployment branches to `main` and configure an appropriate required reviewer. Naming an environment in YAML does not configure protection; GitHub may create a new unprotected environment if it does not already exist.
4. Put these values in that environment, not ordinary repository variables. Use GitHub's secure secret entry or `gh secret set --env android-production NAME` from the owner's trusted machine. Keep credentials out of shell history; the CLI can prompt or read from stdin.

| Type | Name | Value |
| --- | --- | --- |
| Secret | `ANDROID_UPLOAD_KEYSTORE_BASE64` | Base64 of the original upload keystore (JKS or PKCS12); Base64 is encoding, not encryption |
| Secret | `ANDROID_UPLOAD_STORE_PASSWORD` | Keystore password |
| Secret | `ANDROID_UPLOAD_KEY_ALIAS` | Upload private-key alias, never `androiddebugkey` |
| Secret | `ANDROID_UPLOAD_KEY_PASSWORD` | Private-key password; PKCS12 normally uses the store password |
| Environment variable | `ANDROID_UPLOAD_CERTIFICATE_SHA256` | SHA-256 fingerprint of the approved upload certificate, independently checked against the retained original and Play Console after initial enrollment; colon-separated or plain hex |

The public certificate fingerprint can be obtained interactively using `keytool -list -v -keystore /private/path/upload-keystore -alias YOUR_UPLOAD_ALIAS`. Enter the store password only at its prompt. The fingerprint identifies the key; it is not a password. Do not use the app-signing certificate fingerprint from Play Console here: the workflow checks the separate **upload certificate**.

For a locally configured GitHub CLI, pipe the keystore encoding directly into secret storage without printing it:

```sh
python3 -c 'import base64,sys; sys.stdout.write(base64.b64encode(open(sys.argv[1], "rb").read()).decode())' /private/path/upload-keystore \
  | gh secret set ANDROID_UPLOAD_KEYSTORE_BASE64 --env android-production --repo arunkumarmanikonda-web/IG-NEWEST-MARCH26
```

Configure the other secrets using the CLI's interactive prompt, and add the public SHA-256 as an environment variable. Never paste passwords into a command-line argument. The job fails before building if a secret/fingerprint is missing, encoding is malformed, the certificate is expired/not yet valid, the fingerprint differs, or a template debug identity is supplied.

## Build and review

1. Finish source acceptance and store/privacy disclosures. Confirm the app version and increase `android.versionCode` for each subsequent upload in `mobile/app.config.ts`. The initial configured version is `1.0.0` / code `2`; do not reuse a version code already uploaded to Play.
2. From **Actions → Android Play release bundle → Run workflow**, choose `main`. Approve the `android-production` deployment when GitHub requests the environment review.
3. The job installs locked dependencies, runs source/dependency/signing checks, generates a clean Expo Android project, then loads signing credentials for a single build-and-verification step. Secrets are not written to the generated Gradle file. The temporary keystore is removed even on failure and is never included in the artifact.
4. Download the `india-gully-play-release-<commit>` artifact after success. It contains only:
   - `india-gully-play.aab`, signed with the approved upload key;
   - `upload-certificate.pem`, the public upload certificate;
   - `release-manifest.json`, package/version/commit, upload certificate fingerprint and AAB SHA-256.
5. Upload the AAB to the intended Play testing track first, verify Play reports the expected package/version and upload certificate, complete physical-device testing and the required store declarations, then prepare the production release. A workflow success is not Play review approval or publication.

The build verifies signed entries with `jarsigner -verify -strict` against the expected keystore alias, checks the bundle certificate against the pinned fingerprint and checks for the native manifest, bundle configuration and embedded JavaScript. Missing, unsigned, tampered or wrong-key output is not offered as a release artifact. Neither the app's data-room permissions nor website/client authentication are changed by this workflow.

For a local build with the same toolchain, generate the native project and `android/play-release-config.json` as in the workflow, supply the five signing environment values through a trusted secret manager, set `RUNNER_TEMP` to a private temporary directory, then run `node scripts/android-play-release.mjs` from `mobile`. Do not enable shell tracing or Gradle debug logging around secrets.

References: [Android app signing](https://developer.android.com/studio/publish/app-signing), [Android command-line builds](https://developer.android.com/build/building-cmdline), [GitHub Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets), [jarsigner verification](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jarsigner.html).
